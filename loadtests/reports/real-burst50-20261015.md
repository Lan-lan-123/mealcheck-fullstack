# 50 人真实 API 同时上传压测（2026-10-15）

**结论：未通过“已接受任务全部成功”的验收。** 50 个独立账号在 34.803 毫秒内开始发送上传请求，20 个接受、30 个明确返回 429 / UPLOAD_BUSY；已接受任务中 8 个成功、12 个失败，均为 REMOTE_TIMEOUT。查询、数据唯一性、队列排空和服务存活检查通过。本轮结果不支持宣称系统可以可靠完成 50 人突发上传。

## 场景与执行边界

- 独立 Compose 项目 `mealcheck-real-burst50-20261015-164000`，前端 15184、后端 18089，仅绑定宿主机 loopback。项目后缀是证据目录标识；实际运行时间以日志为准：北京时间约 16:03:33 发出突发，16:06:32 左右观察到全部终态。
- 当前工作区后端重新 `mvn -B -f backend/pom.xml package -DskipTests` 构建成功。本轮没有重新运行全套单元/集成测试。将 JAR 复制为本轮固定产物并挂载启动，容器内 SHA-256 匹配 `7242fa8ac436576e7f1ea7b38d8dc60bd4291184855c2958ab9b1784f006f380`。
- Nginx、PostgreSQL、Redis、RabbitMQ、真实鉴权、图片校验、异步任务、保存与列表查询均参与；模型使用本地配置的阿里云百炼 `qwen3.8-max`，没有模型替身。
- 保留上传入口并发 20、图片未完成名额 32、每用户名额 2、消费者 8、全站 AI 名额 10、滚动分钟调用准入 120。后端限制 1.5 CPU / 1 GiB、JVM 堆比例 45%；模型思考模式 off，输出上限 2048。
- 仅在这个临时项目中提高注册/验证码限额以准备测试账号。全站日调用上限设为 110、金额准入上限 10 元，每用户 10 次/2 元；这些是测试防护，不代表真实供应商账单或 token 硬上限。
- 共 51 个新账号：50 个用于突发，每人一张独立幂等键图片；另 1 个先上传校准图，并用于查询已有一条记录的列表。账号和 JWT 仅保存在忽略目录的 `accounts.private.json`。
- 使用已有合成餐食 synth-001～005，转为 1024×1024、约 194～238 KiB JPEG，按账号轮换。没有使用真实用户照片，不代表大文件、慢速公网上传或识别准确率测试。
- 图片字节及 multipart 请求提前准备，通过线程同步屏障释放 50 个请求；34.803 ms 是客户端调用发送操作的跨度，不是服务端接收时间或公网网络同步精度。
- 压测客户端不自动重试；应用自身有界模型重试策略保留。已发送物理 HTTP 重试指标为 0；RabbitMQ 的监听器重试日志不能据此解释为新增供应商调用。

## 失败诊断及后续重试

12 个失败均记录为 ANALYZE 阶段、`REMOTE_TIMEOUT`，摘要为“AI 操作已超过总超时限制”。校准图片完成约 15.79 秒；并发后成功任务也出现明显延迟。证据支持“本配置在这轮真实负载下出现 AI 超时”，尚不足以区分供应商调度、链路耗时、客户端/服务端期限等原因，也没有核实账号实际 RPM/TPM 额度。

未修改代码、放宽超时或增加并发后再次付费重跑。由于首次接受任务未全部成功，**跳过 30 个明确拒绝请求的分批恢复测试**，防止继续增加付费压力。后续建议保持同一批图片，先按实际账号配额验证 1、2、4 个 AI 并发，并记录供应商请求标识和传输异常；在小并发稳定后再复测 50 人突发。不能仅靠扩大入口名额解决已接受任务的超时。

## 本轮用量与不确定部分

本轮应用计数共 30 次物理模型 HTTP 尝试，包含校准；18 次成功、12 次失败，物理重试 0。成功调用已知输入 19,266、输出 2,923，合计 **22,189 token**。按本轮已有配置输入 12 元/百万、输出 36 元/百万估算，这部分为 **0.336420 元**，没有重新核验价格，也没有计入缓存折扣或免费额度。

12 笔失败调用缺少可核对的供应商 usage，不能按零用量计算，**不能报告本轮精确总 token、精确账单或确认剩余 token**。`mealcheck_ai_usage_missing_total=0` 仅覆盖收到响应后执行用量检查的路径，不能证明传输失败请求都有 usage。

数据库 global 日预算 attempts=30、spent=1.911204、reserved=0；包含未知用量失败的保守结算（12×0.131232＝1.574784 元），不是供应商实扣费用。用户层和 global 层记录是同一笔调用的两层配额，不能重复累计。全部预算占位已结束，无 RESERVED/SENT 残留。

30 万 token 是本轮控制目标：校准后预测并监控已知用量，22 万时计划停压，另留在途余量；该监控不是供应商的硬 token 配额。由于存在 12 笔未知用量，本轮没有把“已知 22,189”表述为全部消耗。

## 后续原因分析（同日，只读分析及离线复现）

**业务容量未达标，但不能把 30 个入口拒绝与 12 个接单后失败视为同一种故障。** 如果产品要求 50 人首次上传全部进入任务队列，当前入口上限 20 不满足这个目标；是否允许明确拒绝，应由业务约定决定。无论入口如何配置，接单后 60% 失败都需要处理，不能以“服务没有崩溃”代替业务成功率。

### 已有证据能定位到哪一层

- HTTP 指标明确区分：图片识别成功 9 次、失败 12 次；建议生成成功 9 次、失败 0 次。成功数含校准。12 次失败全部集中在识别阶段，尚未进入建议生成或餐食保存。
- 失败任务执行累计 720.453 秒，平均约 60.038 秒，最大 60.049 秒；图片识别 HTTP 调用最大约 60.010 秒。与当前 remote 总超时 60 秒一致。
- 日志显示，突发后首批多张识别约耗时 51～55 秒，校准识别约 11 秒。这支持真实调用在本轮并发下明显变慢，不证明具体供应商限流或网络根因。
- RabbitMQ 最长排队约 116.66 秒。`MealAnalysisRabbitConsumer` 在领取工作后才调用 `analysisDeadline`，外层操作预算 120 秒；`RemoteCallGuard` 对每次识别/建议调用另有包含重试的 60 秒预算。因此“客户端等了 179 秒”不等于单次模型请求超时设为 179 秒，也不能说排队用掉了这 60 秒。
- 数据库连接池等待数 0、连接超时数 0、最大获取耗时约 4.38 ms；没有 OOM 或容器重启。现有证据不支持数据库连接耗尽、内存不足为这批失败的主要原因。

当前应用固定允许 8 个图片消费者并发，并提供调用次数和并发许可限制，但没有按供应商实时延迟自动降低图片调用并发，也没有 TPM/TPS 与突发增速控制。固定名额是应用侧保护，不是供应商已验证的稳定吞吐。真实可用并发还需按账号额度和延迟实测。

百炼的[限流说明](https://help.aliyun.com/zh/model-studio/rate-limit)和[应对最佳实践](https://help.aliyun.com/zh/model-studio/rate-limiting-best-practices)说明模型会受 RPM/TPM、瞬时频率及流量增速等限制，高并发服务饱和也可能表现为变慢或超时。本次没有取得供应商限流响应或账号侧诊断，不能直接认定“命中某个配额”，也不能排除网络与供应商时段波动。

### 已离线复现的代码缺陷：耗尽期限的失败绕过熔断

`RemoteCallGuard` 的失败计数位于重试循环之后；第一次调用耗尽 60 秒时，后续 `backoff` 或 `remaining` 直接抛出 `RemoteCallDeadlineException`，不经过失败计数。直接抛出的 deadline 异常也会作为 `RemoteCallRejectedException` 提前退出。因此，熔断对这类耗尽期限的失败不能按配置阈值生效。

使用当前已编译业务类、没有网络/数据库的独立 Java 程序，将阈值设为 2、调用预算缩为 1 秒进行对照：

| 离线用例 | 两次失败后下一次是否进入调用体 |
| --- | --- |
| 快速普通异常 | 否，熔断生效 |
| 调用耗尽期限后失败 | 是，绕过熔断计数 |

证据：[DeadlineCircuitProbe.java](E:/mealcheck-fullstack/loadtests/results/real-burst50-20261015-164000/DeadlineCircuitProbe.java)、[复现结果](E:/mealcheck-fullstack/loadtests/results/real-burst50-20261015-164000/deadline-circuit-probe.json)。这是已确认的保护缺陷，会放大下游持续变慢时的问题，但不是最初变慢的根因证明。

同时，`AiChatClient` 对 deadline 异常直接重新抛出，绕过 `aiStatusService.recordFailure` 和高层 AI 失败指标；transport 在没有收到响应的异常路径也没有记录 usage 缺失。低层 HTTP 失败指标仍记录了 12 次失败。这些缺口降低排障和费用核对能力，应补充分类后的异常类型、剩余预算、调用耗时及可用的供应商 request-id，避免记录密钥或完整图片载荷。

### 为什么没有自动恢复

配置的最多两次尝试共用 60 秒，第一次耗满时已经没有第二次尝试的时间，所以物理重试为 0。消费层对终态失败不会自动重新入队重复计费，数据库将其记录为 FAILED，标记 recoverable 仅表示可后续显式恢复。这种防重复计费边界应保留；若业务需要自动恢复，应新增有次数、退避和费用约束的延迟恢复机制，并考虑供应商对超时请求是否仍在执行。

### 修复及复测顺序

1. 优先修复耗尽期限失败的熔断计数和超时可观测性，区分上游超时、许可等待超时、连接异常及 HTTP 状态；保持幂等和费用防护。
2. 用同一组图片验证实际账号的 1、2、4 并发和发送间隔；根据稳定完成率与延迟确定消费者数量。降低并发只是待验证措施，不能预先保证能解决。
3. 在已测延迟分布基础上协调每次调用期限、整个任务期限和客户端等待；单纯增大超时或增加重试可能让积压和费用上升。
4. 确定产品目标：若要求 50 人首次全部接收，应把上传存储与受控 AI 消费分离，并联合评估上传入口、磁盘/内存预算、任务容量及可接受排队时间，不能只改一个 20 或 32。
5. 修复后重新执行同样的 50 人首次突发，将首次接受率、已接受完成率和重试恢复结果分别验收；本轮失败证据保留。

这次后续分析没有修改生产代码、重新启动环境或新增任何付费 API 调用。

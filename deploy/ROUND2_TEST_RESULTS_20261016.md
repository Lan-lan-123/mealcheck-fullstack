# 第二轮测试结果（2026-10-16）

本次按约 4 万 token 的剩余额度优先复测旧问题图片。真实模型使用 qwen3.8-max，关闭思考、单并发、最多一次尝试、每次输出上限 2048 token；本地总预算设置为 38,000 token。没有部署。

## 实际消耗与停止

- 完成 9 张图片的识别、规则评分、真实 AI 建议，共 18 次成功 HTTP 调用。
- 供应商返回输入 27,579、输出 3,324，总计 **30,903 token**。无未知用量、重试或本地建议降级。
- 下一张 synth-029 的调用前预算预留被拒绝，未发送 HTTP 请求。该项记为 BUDGET_STOPPED，后续 5 项记为 NOT_RUN_BUDGET；没有启动第二次付费运行。
- 留下的 7,097 token 本地预算不足以容纳下一次请求的保守输入估算加最大输出，因此提前停止。预算控制按调用前预留与供应商实际用量结算；额度不是必须花满的目标。
- 尚未实测 synth-029、030、075、057、080、001，以及本次优先列表之外的图片；本次不是新的 100 张真实模型全测。

## 重点结果

| 图片 | 旧问题/目的 | 本次结果 |
|---|---|---|
| 021 | 将豆腐餐概括成“有肉” | 新建议正确使用蛋白质、豆制品表述，未称有肉 |
| 026、027、028、074 | 未知餐次被直接称为早餐 | 新建议均使用“本餐”，未断言餐次 |
| 033 | 未提供份量却称“几片黄瓜稍显单薄” | 新建议未断言份量；份量仅作为后续核对建议 |
| 056 | fried 类别导致炸鸡和薯条丢失蛋白质/主食来源 | protein/staple 与独立油炸属性同时输出；分数 0→16，仍保留缺蔬菜、油炸及含糖饮料风险 |
| 051 | 红烧肉 protein/oily 二选一，导致风险与基础结构不一致 | protein 与 highOil=true 同时输出；分数 90→67，基础结构保留并提示高油风险 |
| 076 | 橙汁被视为未知饮品、摘要声称结构完整 | 橙汁识别正常，含糖饮料风险保留，没有结构完整的矛盾表述；评分仍为 0 |

9 张的 27 个食物项均输出基础类别以及两个布尔/空值属性。6 张曾有建议事实越界的图片，在本助手逐条阅读新建议后均未复现旧问题；其他 3 张的新建议也未发现同类越界。该复核不是独立人工验收，9 张合成图的定向结果不代表总体准确率。

相同审核标签下，名称精确/声明别名匹配没有提升：021 新旧均为 1/3，其余 8 张均为 3/3。021 的“酱汁豆腐”“炒四季豆”在语义上对应豆腐与四季豆，但当前标签未声明这些名称；保留原指标，没有为适配本次输出修改标签。因此，本轮证据主要支持分类表达、风险和建议约束改进，不支持声称识别准确率全面提升。

红烧肉的高油标记仍是视觉估计，不能验证实际用油量；白色饮品仍有牛奶/豆浆外观歧义。例如 027 的识别说明承认这项歧义，而模型自报置信度仍有 0.9，不能当作真实正确概率。

- 前端：72 项单元测试通过；TypeScript 检查和生产构建通过。
- 浏览器：17 项通过，接口使用测试桩，没有调用供应商。覆盖纠错的 false/null 保存及重新打开、手动记录属性及改名重置、管理审核属性变化后必须重新确认、移动端流程。
- 标签工具：3 项通过。
- 原 100 张保存结果离线重放：80 个餐食评分和建议请求捕获完成，20 个非食物跳过。数值仅 056–060 共 5 张从 0→16；20 张风险标签变化。10 项旧矛盾结构标签消除，5 张橙汁不再落入未知饮品。没有生成新 AI 建议，没有重跑识别。

未验证真实数据库/队列/Redis/实时检索、完整部署后的端到端流程，也未对旧审核样本自动更新期望分数。规则评分改变符合实现方向，不是独立营养学真值。

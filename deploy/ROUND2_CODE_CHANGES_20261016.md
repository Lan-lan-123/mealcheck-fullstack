## 数据表达

食物的 `category` 表达基础来源，新增独立 `attributes`：

```json
{
  "name": "炸鸡",
  "category": "protein",
  "confidence": 0.95,
  "note": "可见裹粉炸制外层，具体用油量不能确认",
  "attributes": {
    "fried": true,
    "highOil": null
  }
}
```

基础类别为 `staple|protein|vegetable|fruit|dairy|soup|drink|dessert|other`。`fried` 和 `highOil` 分别为 `true`、`false` 或 `null`，表示标记是、标记否、未知。它们是模型估计或人工核对，不代表测量出的实际油量、脂肪量或营养摄入。

两项属性相互独立：非油炸可以有高油风险；油炸食物的油量也可以未知。`FoodItem` 原有四参数构造函数保留，纠错 DTO 原有二参数构造方式保留；新属性为可选字段。

## 后端处理

- 新增 `FoodClassification`，集中处理基础分类、旧格式兼容和风险属性。`MealScoringService.acceptedFoods` 在返回新副本时规范化，不原地修改原始模型食物对象。
- 对旧 `fried/oily` 类别，仅对明确的有限名称恢复基础类别，例如炸鸡归为蛋白质、薯条归为主食、红烧肉归为蛋白质。无法确定原料的“油炸食品”等保留 `other`，不虚构来源。
- 完全缺少旧属性时，保留旧类别表达的风险，并对明确名称保守恢复风险；显式提交的属性对象中，`null` 会继续保持未知，`false` 会继续保持否，不被名称自动覆盖。
- 评分基础结构使用规范化后的类别，风险扣分独立使用已标记的风险属性。更新版本为 `structured-foods-v5`。
- 红烧肉、五花肉等未确认用油量时增加“高油风险待核对”提示，不把菜名当成油量测量直接扣分；明确炸制名称但属性未知时提示“油炸做法待核对”，也不据未知属性扣分。高分摘要会保留待核对事项。
- 识别提示词要求输出基础类别与独立属性，不再要求模型在 protein 与 oily/fried 之间二选一。服务端校验属性的布尔/空值类型，同时接受旧类别以兼容旧响应。
- 饮食建议输入包含两项属性的标记/未知状态及其估计性质，沿用第一轮的事实边界。

## 写入、纠错和历史数据

- 图片分析仍先保存原始识别快照，再规范化用于评分、建议和新餐食 JSON。
- 手动记录、识别纠错、管理端纠错审核都传递属性；审核集指纹和导出中的食物对象随现有序列化保留这些字段。
- 旧客户端纠错时省略属性：对同名食物保留已有独立属性，包括从旧类别恢复的风险；修改基础类别不会静默删除风险。改变名称时不沿用旧食物的属性。
- 新客户端可显式提交 `{ "fried": null, "highOil": null }` 重新置为待核对，或分别提交 `false`。
- 原有食物 JSON 字段直接容纳可选属性，无需新增数据库列或批量迁移。读取旧记录保留旧评分及历史快照；只有新分析、手动记录或主动纠错才应用 v5。
- 新旧评分版本和分类统计口径在历史中并存，不应解释成旧记录已经重新计算。

## 前端入口

- 新增共享 `FoodAttributesEditor`，在识别纠错、手动记录和管理端审核中分别选择“油炸做法”“高油风险”的是/否/待核对。
- 新基础分类选项移除独占的“油炸”“高油”；旧记录进入编辑时按与后端一致的有限映射转换，风险保留为独立属性。
- 修改食物名称时重置属性为待核对，避免把上一种食物的风险带到新名称上。低置信度食物的原核对流程仍保留。
- 结果页显示已标记的风险属性。API 类型及运行时校验保留新字段，允许旧响应缺少属性；不将字符串/数字强制解释为布尔值。
- 管理员修改审核食物或属性后，需要重新勾选审核确认。

## 两处实际缺陷

### 无标签密封袋被直接当作非食物

`package-03` 是完全不透明、无标签的密封袋，不能确认内部是否有食物。固定预期允许 IMAGE_UNCLEAR，或不计分的未确认候选。

实际三次均返回 `foodImage=false`、`sceneType=NON_FOOD`、`foods=[]`。首轮理由为“图片中为密封包装袋，无可见食物或饮品”。模型把没有看见内部内容当作了非食物证据。

按当前 `MealAnalysisService` 的业务路径，这类返回会进入非食物分支；如果直接用于真实上传，还可能累计非食物上传次数。本轮只运行识图解析与评分组件，没有写入用户惩罚记录或执行业务数据库请求。

### 不透明纸杯被高置信度放行并计分

`package-04` 是盖子闭合、标签不可读的纸杯，看不到内部内容。预期只能是不清楚，或低置信度未确认候选且不计分。

实际三次均命名为“外带热饮”，类别 `drink`、置信度 **0.95**。其中两次依据包装外观联想到咖啡/茶，第三次也仅凭“典型热饮包装”作判断；没有读到具体饮品标签或看到液体。

生产候选过滤阈值为 0.5，这个泛称因模型给出了高置信度而进入评分，产生了 **2 分**的结构评分和“饮品类型未知”等提示。它没有明确输出实测含糖量、容量或具体克数，但仍把无法确认内容的容器变成了可评分的饮品。

这里的问题是看不到内容时的过度确定和错误放行；不能把纸杯外形证明成实际有饮料、热饮温度或成分依据。本轮自动规则报告的 `GUESSED_OPAQUE_DRINK_INGREDIENTS` 表示无依据地联想到饮品成分，并不表示模型三次都声称了确定配方。

这两处本轮尚未修改生产逻辑。下一步应优先明确“内容可见/标签可读/内容被隐藏/可确认空容器”的识别依据，并将隐藏内容与计分资格分开约束；增加非食物处罚前对“未知内容”的区分。不能只降低所有图片的置信度，也不能把密封包装一律放行或一律拒绝。

## 后端、页面与验收范围

- 新入口 `VisionEdgeLiveTest` 默认不启用。显式开启后使用生产识图提示词、真实 HTTP 传输、生产解析、语义校验、`acceptedFoods` 过滤和结构评分。
- 新增 `VisionEdgeCriteria`、`VisionEdgeCriteriaTest`，检查未知内容不能以具体食品名或高置信度泛称混过验收，以及不能虚构克数、容量或能量。原始响应保留，规则不代表完整的语义审核；本轮另逐项核对了实际输出。
- 本轮没有出现被评测规则识别到的测量值编造；没有把两张空包装或两个污渍场景识别成可评分食物。这不证明所有识图风险属性和营养判断正确。
- 本地预检/回归 **18 项通过**：10 项既有边界契约、7 项评测器检查、1 项文件/标注预检；预检模式不读取密钥、不调用模型。
- 浏览器 **12 项通过**，验证低置信度候选独立展示、确认后才能纳入纠正，以及 IMAGE_UNCLEAR/NON_FOOD 的换图提示、刷新恢复、请求标识、重试和手机布局。浏览器使用 API 拦截，没有把拦截结果称为真实模型识图。
- 测试中的 `effectivePipelineCode` 按当前业务过滤分支映射；本轮未执行完整上传 HTTP、数据库保存、真实知识召回或建议生成，且没有重新部署业务容器。少量剩菜的结构评分仅验证程序能否过滤/计分，不能解释为对整餐、实际摄入量或健康程度的测量。
- 初次预检因工具注册器构造参数在项目并行更新后不匹配而未编译通过；重新预检时该旧入口已被适配。本任务没有覆盖或回退相关业务更新。初次日志保留，不改写为成功。

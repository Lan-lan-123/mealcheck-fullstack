# 认证说明

**当前协议：HttpOnly Cookie、CSRF 与 PostgreSQL 持久化撤销。** 实现、升级、数据库恢复和工具适配见 [Cookie 认证加固（2026-10-26）](AUTHENTICATION_COOKIE_20261026.md)。以下内容是 V47 的历史协议与当时待办，不代表当前认证方式。

## V47 历史记录

认证仍使用 Bearer JWT、Redis 撤销名单和数据库用户查询，不使用 HTTP Session。

## 本次升级

- 先应用 Flyway V47，再同时升级所有后端实例。数据库增加 `users.enabled`（已有用户默认正常）和 `users.token_version`（默认 0）。避免新旧认证代码混跑：旧实例不检查封禁状态，也不识别新的撤销键。
- 新 JWT 包含随机 UUID `jti` 和认证版本 `ver`。缺失或无效的字段会导致认证失败；升级前签发的 JWT 需要重新登录，不继续兼容旧令牌。
- 退出时，经过验签的 `jti` 写入 `auth:blacklist:jti:<jti>`，TTL 为令牌剩余有效期。受保护请求检查撤销名单；Redis 读取失败返回 503。
- 管理员在“用户管理”中封禁、解封普通用户。接口为 `PUT /api/admin/users/{id}/status`，请求 `{"enabled":false}` 或 `{"enabled":true}`。只有管理员可操作，不能修改管理员账号的状态。
- 状态变更在数据库事务和用户行锁下执行，并记录 `BAN_USER` / `UNBAN_USER` 审计。同状态重试不重复增加版本或生成审计。
- 被封禁账号不能登录，已有 JWT 在下一次鉴权时返回 401。每次实际状态变更增加 `token_version`，解封也不会恢复旧令牌，必须重新登录。封禁不删除业务数据，也不取消已通过鉴权的请求或后台任务。

## 正式上线前待办

- 评估将浏览器认证凭证从 localStorage 迁移至 HttpOnly、Secure、适当 SameSite 的 Cookie，并同步设计 CSRF 防护和跨域配置。当前仍使用 Authorization Header，不要仅切换 Cookie 后继续沿用关闭 CSRF 的设置。
- 核实实际 Redis 部署的 AOF 同步、持久卷、备份和恢复策略，以及内存策略，避免撤销记录被提前淘汰。生产 Compose 已开启 AOF 并挂载数据卷，但这不等于所有故障下都不会丢失最近的写入。
- 演练 Redis 数据丢失后的认证处置：黑名单为空且服务恢复可达时，未过期的已退出 JWT 可能重新通过。需要明确恢复目标及必要时让所有凭证重新登录的流程；不要随意轮换 JWT 密钥，项目部分其他密钥配置也可能回退使用它。
- 验证多实例退出撤销、封禁、解封、依赖不可用返回 503，以及恢复后旧撤销记录仍存在。

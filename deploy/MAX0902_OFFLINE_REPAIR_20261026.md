# Max 实测后的离线修复

本轮依据 `MAX0902_FULLCHAIN_RESULTS_20261026.md` 和已保存的原始结果修复代码。真实模型额度已耗尽，本轮不调用百炼或 SiliconFlow，不修改模型选择，不重建知识库，不重启当前业务容器。

## 已实现的变化

### 时间预算与准入

- HTTP 单次超时从实际派发时开始；排队时间仍计入远程操作总截止时间及调用方上下文截止时间。重试共享原操作截止时间，不为重试重新延长总预算。
- 准入结束、预算预留结束及派发前重新检查剩余时间。默认至少保留 1000 毫秒可用 HTTP 时间，避免原实测中排队 9.916 秒后仅留下约 91 毫秒执行重排。1000 毫秒是防止无效派发的保护门槛，需要额度恢复后按各阶段真实耗时验证，不能称为最优参数。
- 新增 V51 迁移 `ai_call_waiters`：跨实例按入队序号选择最早可执行的请求。后台请求用完其额度后，允许交互请求使用原有预留名额；取消移除票据，崩溃票据按截止时间过期，队列默认最多 1024 条。
- 本地准入超时与模型服务失败分开处理，不用准入等待触发供应商熔断。保留原取消和总截止传播，建议服务也不得将取消结果转换成可保存的规则建议。
- 增加 `mealcheck.ai.admission.duration`，分别观察 accepted/rejected 的准入耗时；HTTP 执行耗时不包含排队。保留已有 HTTP 派发等待日志。

原有 40 个图片消费者、全局 42 个调用许可、每分钟 120 次启动、400 毫秒最小启动间隔及 30 秒复核预留均未调整。本轮尚无证据证明应把它们改成某个最优值；每分钟启动限制仍会约束多阶段流水线的吞吐量。

### 建议降级

- 区分 `FACT_CONFLICT`、`UNKNOWN_ATTRIBUTE_ASSERTED`、`UNNEEDED_REVIEW` 和 `EMPTY_ADVICE`。原因进入日志与固定标签的 `mealcheck.meal.advice.validation` 指标，不写入模型原始回复或个人内容。
- 确认的否定属性与未知属性分别处理；只删除唯一问题为无依据核对请求的句子，不通过删句隐藏事实冲突。
- 补充“未识别为油炸”“高油风险尚不明确”等表述的识别，保留食物及属性作用域的检查，避免将其他食物的限定词套用过来。
- 原实测中 30 条降级前建议未保存，不能回推它们全部是误拦截，也不能据本轮改动宣称真实降级率已下降。

### 结论与引用

- 果干的类别判断按分句检查，后文“仅凭外观换算”不能替前文“一概不能替代”补上限定条件。
- 增加“可能差异/可能包含”被写成确定结论的保护。差异规则同时限制断言位置和属性主题，避免误拦“不同店铺”等修饰语，或把配方不确定性套到体积事实上。
- 以“且”开头的独立结论要求补全；部分审核通过时，不得把依赖前文的片段单独展示。
- 规则用于已知边界保护，不能代替完整语义审核。

## 上线与下一轮

这些改动需要构建新版后端，并在启动时应用 V51。正在运行的旧容器不会自动获得源代码改动。新旧实例的混合部署期间，旧实例尚不使用新队列，不能视为公平调度已经全面生效；部署时应先排空旧任务，再切换全部后端实例。

额度恢复后，使用同一批固定问题及合成图片按阶梯并发复测。验收重点是成功保存率、分阶段排队/执行 P50/P95、超时归因、建议降级原因、最终结论及引文是否支持，以及复核预留是否生效。原实测 34/50 保存率及准确性数据不能用本轮离线结果替换。

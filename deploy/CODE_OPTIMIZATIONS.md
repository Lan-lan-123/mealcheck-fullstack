# 代码优化与接口变更（2026-10-13）

## 七项改动

1. **统一数据刷新**：成功修改餐食、饮食方向、行为目标或计划时，API 层发布 `mealcheck:diet-data-changed`。趋势、当前周报、目标和计划使用相关数据的版本作为缓存键；隐藏页面只失效缓存，不主动发请求。失败请求不发布变更。周报任务完成还会通知历史列表刷新。
2. **分页与直接查询**：行为目标、行动计划使用分页响应；编辑时按 `user_id + id` 查询，保存后同样直接读取结果，不依赖第一页。统计所用目标按日期范围查全量，不受列表分页影响。
3. **连续新建计划**：手动计划保存后重置行动内容、标题和日期，可继续新增；从同一建议保存计划后仍禁用该建议的保存按钮。失败时保留草稿。
4. **助手任务生命周期**：`AssistantTaskManager` 统一维护排队、运行、完成、失败、取消和超时。期限从提交时建立，并继承入口操作期限，包含排队时间。取消会移除排队的 `FutureTask`；正在运行的任务取消后，等清理结束才释放同一用户的准入。提交被接受后先返回 `queued` 事件和请求 ID，浏览器在模型开始前也能取消。超时通知和底层连接关闭使用同一任务状态。
5. **聚合统计**：数据库一次按业务日期与餐次聚合餐食，不再读取逐餐数据反复扫描。覆盖率、去重餐次和目标进度复用同一结果；累计达标天数使用前缀计数。餐食聚合、目标、未吃声明和计划状态共四次读取，查询次数不随目标数量增加。
6. **周报保留与范围失效**：V29 给快照增加 `stale` 和 `invalidated_at`。餐食新增、删除、纠正或跨日修改，只使包含受影响日期的报告及任务失效；旧快照保留。只改备注、餐次声明、行为目标或计划时，保留报告正文，当前报告在读取时附加最新覆盖率、目标和执行情况。饮食方向变更保守地使该账户全部报告过期。当前周报只使用截至今日的有效快照，旧周期通过历史列表查看。
7. **后端职责与类型**：目标逻辑在 `BehaviorGoalService`，计划逻辑在 `ActionPlanService`，统计逻辑在 `TrackingStatisticsService`，SQL 查询在相应 Repository。原 `BehaviorTrackingService` 仅保留薄的调用入口。响应类型独立于 Service，统一放到 `TrackingDtos`；新控制器不直接执行 SQL，不再返回不明确的 `Object`。相关依赖改为构造器注入，助手两种接口统一限制问题及历史长度。

营养估算仍默认关闭且明确提示不准确，继续独立于行为目标。

## 分页契约

`GET /api/profile/behavior-goals?page=0&size=20` 与 `GET /api/plans?page=0&size=20&from=2026-10-01&to=2026-10-31` 返回：

```json
{"content": [], "totalElements": 0, "totalPages": 0, "page": 0, "size": 20}
```

页码从 0 开始，每页 1–100 条。计划查询仍支持省略日期，默认过去 30 天至未来 90 天；日期范围最多 366 天。新增和修改接口仍返回单条保存后的对象，版本与所有权校验保持。

外部客户端若曾按数组解析 GET 结果，需要改为读取 `content` 和分页字段。项目新前端接受分页响应；兼容数组仅用于旧版本或测试桩，不将它作为新接口契约。

## 历史周报

- `GET /api/reports/weekly/history?page=0&size=20`：本人历史快照元数据，包含是否过期。
- `GET /api/reports/weekly/history/{id}`：`snapshot` 元数据与原始 `report` 内容。保留生成时的数据，不用当前目标或餐食覆盖原快照。
- 当前周报及成功任务状态读取时附加实时统计。历史报告显示“已过期”不代表删除，也不代表它是当前周期的统计。
- 历史生成时间允许为空，列表和详情会显示未知时间，避免兼容旧数据时报错。
- 周期元数据缺失的旧快照，在餐食变动时保守标为过期；仍可通过历史接口读取。

## 助手排队与校验

新 SSE 顺序为 `queued` → `meta` → `delta` → `complete`，异常返回 `error`。`queued` 即提供 `requestId`。取消使用原有 `DELETE /api/assistant/requests/{requestId}`，仅作用于本人任务。

工作线程默认 4 个、队列容量默认 16，可通过 `mealcheck.assistant-delivery.workers`、`mealcheck.assistant-delivery.queue-capacity` 调整。总期限仍使用既有 `mealcheck.ai-budget.operation-timeout-seconds`。任务注册位于单个后端进程，当前本地部署为单实例；多实例部署需另行设计任务路由或共享注册机制。

问题最多 4000 字，客户端历史最多 20 条、每条最多 8000 字，角色仅允许 user / assistant。前端提交历史时截取单条长度，服务端验证不依赖前端。真实模型测试本轮继续暂缓，流式、取消和期限使用本地模型桩验证。

## 验证重点

- 121 个目标下分页与旧 ID 修改；601 个计划下最后一页和总数准确；跨账户操作拒绝。
- 120 个目标与重复餐次下餐食只聚合一次，去重餐次及达标天数正确。
- 无关计划 / 目标 / 备注变化保留报告，餐食跨日修改使新旧日期的报告过期，其他周期保留。
- 原始历史正文不变，过期报告不会被当作当前报告。
- 队列取消立即释放容量、本人取消校验、排队计入期限、运行清理期间阻止同用户新任务。
- 前端立即刷新新进度、失败时缓存保持、翻页编辑、连续创建计划、排队阶段取消及历史报告展示。

本轮工作区还包含 V30 的任务失败引用与 V31 的查询索引迁移，保留原改动并进行兼容性验证；V31 按其 `.sql.conf` 使用非事务方式创建并发索引。部署前后联合备份、恢复演练与实际运行验收记录见 README。

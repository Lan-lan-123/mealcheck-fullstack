# 2.0.0 本地CI预验收（2026-10-30）

已在本机补跑CI关键环节，并发现、修复了实际的容器启动问题及过期验收契约。原先仅凭局部测试判断“等待上传即可”依据不足；现在通过的本地运行证据更完整，但仍不等于GitHub对最终候选提交的验收结果。

## 发现和修复

1. **容器根目录启动失败。** `AssistantReviewDiagnostics`直接调用工作目录的`getFileName().toString()`；在`/`启动的容量/双后端容器中目录名为null，Spring无法初始化。增加根目录处理及跨平台回归测试，不修改证据校验策略。
2. **Redis故障断言过期。** 容量脚本仍要求Redis停止时认证失败；当前令牌撤销保存在PostgreSQL，已有登录态应继续读取。分别验证Redis故障时返回有效分页结果、PostgreSQL故障时返回`503/AUTH_DEPENDENCY_UNAVAILABLE`，并补测反例；没有放宽负载阈值。
3. **助手测试桩格式过期。** 所有权测试使用个人趋势任务，继续核对真实模型桩输出、完整历史及跨实例任务状态。知识恢复测试则让桩从本次实际检索结果选择原文及段落ID，按现有逐断言格式复核，拒绝不在绑定原文中的断言；不再依赖固定“测试建议”字样。新增测试覆盖缺来源、未支持文本和JSON字段顺序。
4. **知识源验收数量过期。** 旧默认200实际上对应旧知识版本；当前正文为200主题、1351片段。默认期望数量改为读取版本库的知识元数据，实际仍验证冷启动只计算一套向量、唯一片段数、重启不重算及租约接管。
5. **Docker构建诊断输出。** 保留Maven构建信息，便于区分依赖解析耗时和编译错误。第一次旧源码构建在修复后主动停止；修复后的Linux源码镜像构建完成，不将中断轮次算作成功。

## 后续干净环境复查

- 普通CI原先直接发现并运行评测工具测试，其中一个用例使用`logs/backend/`作为临时文件父目录。本机历史目录掩盖了新检出环境缺目录的问题。已在不含历史日志、依赖目录或构建产物的源码副本中复现`FileNotFoundError`，随后改用现有统一测试入口；该入口创建所需目录并集中临时文件，120项测试全部通过。
- 发布脚本补齐生命周期契约、助手契约和双后端助手/知识源验收，并校验两组结果与同一候选JAR的SHA256一致；报告和日志同步纳入归档及哈希清单。12项发布契约通过，含错误JAR报告不能放行的反例。
- 冷构建、双后端重启和恢复检查均可能耗时；常规CI与发布工作流的总超时分别从35/45分钟调整为45/60分钟，测试判定与性能阈值不变。两份工作流YAML及shell语法检查通过。
- 本轮证据：`logs/deploy/ci-clean-review-20261030/`、`logs/deploy/ci-clean-evaluation-review-20261030-185938-745034.log`、`logs/deploy/ci-review-release-contracts-20261030-190019-233376.log`。源码副本中的评测材料使用已验证的1351片段清单重新组装离线计划，用于验证测试的目录与输入依赖；没有在该副本重新编译后端。

Windows上的后端测试、Linux中的镜像/代理/容器验收，与GitHub的全新Ubuntu runner仍有差异。后续必须审查并提交所有必要文件，对这个确定的提交运行GitHub CI及`release-baseline`；通过前不创建正式发布标签。本地证据增加了通过的把握，不保证远程一定通过。

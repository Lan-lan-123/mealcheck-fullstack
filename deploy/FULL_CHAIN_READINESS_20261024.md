# 全链条测试就绪评估

2026-10-24，Asia/Shanghai。本轮只做只读配置、源码与本机运行条件检查，没有调用向量、重排、语言或识图接口，也没有重建知识库。

## 判断

项目已经具备开展完整 RAG 和餐食分析评测的代码基础，但**当前本机环境尚不能确认就绪**。不能因为向量模型已重新部署，就认为既有知识向量、当前生效配置和业务服务已匹配。本轮没有实际跑完任何全链条案例。

## 已核实与待核实

| 项目 | 本轮证据与状态 |
| --- | --- |
| 本机 Docker | Docker 命令无法连接 `dockerDesktopLinuxEngine`，提示管道不存在；进程查询未找到 Docker Desktop/后端进程。当前无法查询容器和数据库 |
| 后端/前端健康 | 后续只读 HTTP 检查因自动审批服务自身 HTTP 403 未执行；不能据此声称业务 HTTP 接口报错或不可达 |
| 文件中的文字与识图配置 | `.env` 均为 `qwen3.8-flash`，密钥已配置；不等同于已读取正在运行的后台配置 |
| 文件中的重排配置 | `.env` 启用 `qwen3.7-text-rerank`，地址及密钥已配置；真实请求成功、是否降级尚未验证 |
| 文件中的专用向量配置 | `.env` 未设置专用模型、地址、维度与密钥。后台可以持久保存管理员向量配置，必须读取数据库/后台当前生效值；不能据此认定用户尚未部署 |
| 实际向量模式 | 尚未读取 `knowledge_embedding_settings`，无法确认是否为 `SEMANTIC`。代码在没有管理员选择且未提供完整专用配置时可能选择 `LOCAL` 哈希模式 |
| 生效连接与索引匹配 | 尚未读取 active/draft profile、实际维度、索引签名、过期片段及重建任务状态，均待核验 |

后台保存待用配置、连接测试成功与配置/索引正式生效是不同阶段。应检查当前 active profile，而不是只看 draft 或 `.env`。`KnowledgeEmbeddingService` 支持在指定条件下复用百炼文字接口凭据，故缺少专用 key 也不能单独证明语义向量不可用。

如果此次部署位于另一台服务器，本机检查不代表远端状态；需对实际业务后端、数据库及对应向量连接执行同样核验。

## 现有评测入口需要适配

`RagLiveQualityDatabaseIntegrationTest` 可作为基础，但不能直接视为当前已部署链路的验收：

1. 使用 Testcontainers 创建隔离 PostgreSQL，再将整个知识集重新向量化。它不直接检查本地现存索引，会产生额外的向量请求。
2. 向量维度硬编码为 512，读取 `.env` 的专用配置，不加载业务数据库中管理员保存的当前 active profile。
3. 虽然构造了 `KnowledgeRerankerService`，但没有显式从 `.env` 加载重排开关、地址、模型和密钥；是否真实重排不能由“构造了服务”证明，仍可能走本地降级。
4. 使用模拟的缓存、用户历史等依赖，没有经过真实业务 HTTP、鉴权和持久化入口。

`tools/evaluation/run_live_rag_screening.py` 是另一个严格限定用途的历史入口，主要测切块与向量召回，明确禁止 Chat 和 rerank，不适合作为完整链路测试直接运行。本轮没有绕过它的授权范围或使用会触发全库重建的旧命令。

## 启动全链条测试前的门槛

- 对实际部署地址确认后端、PostgreSQL/pgvector、Redis、RabbitMQ 正常，且没有并行重建、切换配置或迁移。
- 读取生效向量模式、模型、地址、维度和发送维度参数；发起受控向量探测，确认非零、有限数值及维度正确。不能把哈希兜底或缓存旧响应当作本次真实向量调用。
- 核对库内 embedding signature 与当前查询签名一致。仅模型或维度表面相同仍不够；如果确实换了向量空间，应完成对应重建再测。若只是同一模型服务恢复且签名一致，不预设必须重建。
- 核对知识片段数量、来源版本、是否有过期/混合签名，及重建任务是否完成。旧批次 1351 条片段只是历史快照，不能代替本次核对。
- 确认重排服务真实调用成功、候选有原始模型分数与重排标记；降级规则单独记为降级，不能算作重排成功。

## 建议测试顺序

先进行 10 题小规模冒烟，确认每个阶段可观察，再扩展为 30–50 题分层验证，最后运行完整题集与独立留出案例。题目、允许外发的知识片段、请求/费用上限和停止条件须在真实调用前固定，不先全量重建或运行旧大批量命令。

### 知识问答链

真实请求 → 当前生效模型生成查询向量 → pgvector/混合召回 → 真实重排 → 证据选择 → 回答生成 → 引文存在性及逐分句语义复核 → 补检/追问 → 最终 API 和页面。

逐题保留检索前后来源/片段标识、粗排及重排位置、重排原始分数、实际供应商调用、最终保留结论与引文、信息不足状态、补检次数、拒答原因和耗时。检索命中、答案有引用、引用实际支持结论应分别评分。

### 餐食分析链

图片上传 → 识图及不确定性处理 → 候选过滤/评分 → 生成检索查询向量 → 召回与重排 → 证据支持的建议 → 任务状态 → 数据保存 → 页面展示。

这条链还需检查未确认内容不计分、失败不生成成功记录、数据库保存与页面一致、错误提示及重新上传行为。此前测试出的无标签袋、封盖纸杯、同时缺输入和知识、因果词规则误删等案例均应纳入回归；不能因为接入向量后链路能返回答案，就将这些质量问题视作已解决。

## 验收口径

| 层次 | 主要检查 |
| --- | --- |
| 运行链路 | 各阶段真实执行、无隐蔽降级，任务/存储/页面状态一致 |
| 召回 | 对固定相关性标注计算 Recall@K、排名指标，并查看漏召回的关键证据 |
| 重排 | 比较重排前后关键证据位置，独立记录降级与供应商错误 |
| 回答 | 原问题回应、引用存在性、结论支持度、数量/条件/因果边界、信息不足分类与补检 |
| 识图与评分 | 食物/非食物/无法确认的区分，未知内容不冒充事实、不错误计分 |
| 运行成本 | 分模型请求数、缓存命中、token/用量、耗时与错误类别 |

同模型自动评审与助手编写的既有标注只能作为代理指标，不能替代独立人工复核。应报告“链路是否跑通”和“质量是否达标”两个结论。

本轮结论：**可以准备并进入分阶段全链条测试；当前本机运行状态和索引匹配尚未通过前置核验，不能宣称已就绪或已通过全链条评测。**

# 对话选餐与 Function Calling 演示

## 启动条件

- 使用支持工具调用的模型，并配置现有模型服务参数。
- 开发配置默认开启 `MEALCHECK_ASSISTANT_FUNCTION_CALLING_ENABLED`；生产配置默认关闭，需要显式设为 `true`。
- 重启后端或重新构建、启动后端容器后，Flyway 会执行 V46，为历史消息添加工具记录字段；前端也需使用本次构建。
- 将演示账号的偏好和饮食目标按实际需要设置。推荐服务读取当前登录账号，不接受模型传入 `userId`。

## 演示步骤

1. 打开网页右下角饮食聊天助手，输入：`晚餐在家做，预算25元，30分钟内准备好，推荐下一餐搭配。`
2. 展开回答下方的“工具调用记录”，查看 `recommend_next_meal` 的参数、发起来源、结果摘要、轮次和耗时。实际由模型发起的记录标为“模型发起”；没有调用时不会伪造记录。
3. 追问：`改成外卖，预算还是25元`。检查新的工具参数 `scene=TAKEOUT`，其他已明确条件保留。
4. 新建对话并问：`推荐下一餐搭配`。助手应询问缺少的餐次、场景、预算和准备时间，不凭空填写参数。
5. 新建对话并问：`晚餐在家做，预算1元，5分钟内准备好，推荐下一餐搭配`。搭配库无匹配时明确说明，不自行放宽预算或移除忌口。
6. 重新打开历史会话，工具调用记录仍可查看。

费用和时间来自项目搭配库。费用不是实时商家报价；时间是准备或选餐参考，不包含排队、配送。对话不会下单、写入行动计划或修改偏好。临时新增忌口不属于本工具的输入，应先在饮食偏好中设置。

## 实现位置

- `AssistantRequestPlan`：识别选餐及连续条件修改，限制可用工具，不预先执行推荐。
- `AssistantFunctionCallingService`：将工具说明发给模型，执行真实工具请求，回传结果并继续生成；保留调用证据。选餐参数错误可回传模型修正，仍受总轮数、调用数和期限限制。
- `AssistantFunctionToolRegistry`：注册和严格校验 `recommend_next_meal` 参数，调用已有 `NextMealService`，应用账号偏好、目标和近期记录。
- `LangChainDietAssistantService`：网页 SSE 请求同样走选餐工具循环；关闭开关、模型不可用或查询失败时明确提示使用原有“下一餐搭配”面板。
- `AssistantToolCalls`：展示调用证据；记录由服务端持久化，前端历史输入中的记录不用于证明真实调用。

## 验证

后端测试覆盖路由与连续追问、模型调用与结果回传、参数校验和用户身份、无匹配方案、SSE 接入及调用记录保存和恢复。前端测试覆盖 SSE/历史接口校验；浏览器测试覆盖两轮参数变化、记录展开、历史恢复及桌面/移动布局。

测试使用可控的模型替身，不代表真实模型一定会选择同一工具或参数。面试前用实际配置的模型按以上步骤演练，并以实际工具记录为准。

### 真实模型验证

`MealPlanningRealModelTest` 是额外的付费模型实测入口，默认跳过，只有显式设置 `MEALCHECK_LIVE_MODEL_VERIFY=true` 才会调用 `.env` 或进程环境中配置的模型。输出目录由 `MEALCHECK_LIVE_MODEL_OUTPUT` 指定，必须位于项目 `logs/` 内。单次运行最多 12 次远程请求，不重试。

这个入口使用真实的 `AssistantChatModelFactory`、`AiHttpTransport`、`AssistantFunctionCallingService`、工具注册表和搭配库；空餐食、默认偏好、目标及数据库配额/并发许可使用隔离夹具。它验证真实模型的工具选择、参数与结果回传，不替代网页 SSE、数据库持久化和额度账本的应用联调。证据只保存模型名、响应 ID、Token 用量、工具参数及最终回答，不保存密钥、请求头或模型推理内容。

2026-10-24 首轮真实模型测试发现，模型可能直接改写上一轮方案，或在预算为 1 元时不查询而自行认定不可行。后端因此增加以下约束：当前输入明确给出合法餐次、场景、预算及时间时，要求模型发起推荐查询；其他请求保留自动选择和追问。模型仍生成工具参数，后端校验并执行；查询完成后恢复自动模式。若模型未经本轮查询就声称已查询，系统在既有轮数和期限内要求纠正，最终仍不能伪造成功。

真实模型与业务工具循环的四组场景已通过，完整应用联调仍受本机 Docker 故障阻塞。结果、修复及范围见 [2026-10-24 实测记录](FUNCTION_CALLING_REAL_MODEL_20261024.md)。

完整应用的真实 SSE 验证另有脚本：

```powershell
python deploy/scripts/verify_function_calling_live.py --base-url http://localhost:8080
```

它创建唯一临时账号，经真实聊天接口验证四组场景，核对实际搭配和已保存的调用记录，然后删除临时账号。加 `--isolated` 可使用当前构建的后端 JAR、新建 PostgreSQL/Redis 临时容器及 `.env` 中的真实模型；需要 Docker 正常运行且对应镜像已缓存。日志、结果和临时后端文件默认放在新建的 `logs/backend/function-calling-live-时间/` 下。

执行测试时使用 `tools/run_logged.py` 保存日志，报告和截图输出到本次的 `logs/` 批次目录；不要使用源码目录下的默认测试结果路径。
